# Life Pilot 雲端成本與收費建議

日期：2026-10-30。以下是提案，尚未改動資料庫的售價或既有購買額度。
目標：每月全體使用者與廠商合計淨收益 NT$50,000，不是每帳號各收益 NT$50,000。
目前平台皆為免費方案；未取得實際儀表板的資料庫大小、流量、CPU、記憶體及收款合約，因此不能保證用多少帳號就足夠或何時必須升級。

## 一、先辨認成本瓶頸

- Supabase Free：500 MB 資料庫、1 GB 檔案儲存、5 GB 一般流出、另外 5 GB 快取流出，50,000 MAU。API requests 雖未按次數設限，仍受運算、流量及服務限制；兩種流量不能當成資料庫查詢共用的 10 GB。
- Supabase Pro：US$25/月起，第一個專案包含在方案中；列出的包含量為 8 GB disk、100 GB Storage、250 GB 一般流出與另外 250 GB 快取流出。額外專案、較大 Compute、附加功能及超額用量可能另計。
- Render 免費服務：同一 workspace 合計每月 750 instance hours，不是每個服務各 750；服務閒置休眠不消耗運行時數。既有信件列出的四個服務會共用此池，不能把全部支出歸給 Life Pilot。減少 API 次數不一定等比例減少運行時數；不應新增保活呼叫。
- Render 付費 Web Compute 最小列價 US$7/月；workspace 方案、Compute、流量、建置用量要分開看，不能只升級 workspace 就消除免費服務限制。

### 專案目前特別需要注意的成本

1. 圖片曾以 base64 放在資料表欄位；這會占用 database，而不是獨立 Storage 額度。不能看到 Storage 尚有空間就認為 database 安全。base64 本身通常比原始二進位大約多三分之一，還未計索引等成本。
2. 過去實測回憶 24 筆回應約 1.4 MB，幾乎都是圖片。若每次都傳 1.4 MB，30 人每天讀四次、30 天，約為 5 GB；這是說明風險的假設，並非目前實測月用量，也未扣除既有延遲載入與快取改善。
3. 公開活動與景點沒有付費也可能被大量瀏覽。只有「可建立筆數」限制不足以控制讀取流量，免費瀏覽也有成本。
4. 到期活動保留一年供成效查詢；取消訂閱不會讓這些資料和成本立即消失，不能以取消人數直接推算可降級容量。
5. 不能把 service_role、外部 API 密鑰放進客戶端可讀的 table。需要密鑰、爬取及管理者操作的工作仍留在可信任後端。

## 二、本輪實作與邊界

- 將額度刷新所需的訂閱狀態、使用量、購買明細、累計額度、投稿數量組成一個 bootstrap RPC。
- 合併 RPC 主要減少連線往返與資料傳輸；函式內仍需執行既有統計查詢，不代表資料庫 CPU 用量也按相同比例下降。
- 新 RPC 未部署時，只對明確的 PGRST202 回退到舊 Supabase 讀法；權限、額度或資料庫錯誤不繞道 Render。
- 舊讀法的活動／景點筆數改成 exact HEAD count，不下載所有 ID，也不受清單回傳 1,000 筆等上限導致少算。
- 未設定適用額度回傳明確狀態，不繼續執行其他用量查詢；畫面顯示四語系唯讀提示。
- 雲端 SQL 加上 statement-level 新增／修改／刪除防護，本機在 LocalDataStore 執行防護；管理員不被鎖住，以便建立第一筆設定。
- 修正收費版本表 answer_history_days 的 constraint 不接受 0，與既有 RPC／表單允許 0 不一致的問題；不修改現有價格和購買明細。
- 補齊「更新原版本」缺少的活動／景點額度參數。
- 股票雲端讀寫流程、既有提醒同步及例行清理沒有改動；沒有購買或取消任何平台方案。

SQL 尚須在 Supabase 手動執行；本機測試不代表線上已部署。SQL 檔仍按既有規則不納入 Git。
第一個腳本：tool/supabase_pricing_history_zero_20261030.sql。
第二個腳本：tool/supabase_subscription_bootstrap_20261030.sql。
兩份腳本已在獨立的 PostgreSQL 17 測試資料庫執行通過，包含免費預設、付費累加、CRUD 拒絕、模式隔離與廠商分類；另重跑既有 39 個參數化額度檢查。測試資料庫已關閉並刪除。
測試環境的訂閱狀態／累計查詢部分使用隔離替身，不能代替正式 Supabase 的部署驗證。執行前仍須核對正式資料庫函式、欄位及觸發器，特別是搬移與分享流程。執行後完整重啟 App 或重新整理網頁，不只 hot reload。

## 三、建議對外方案

以下為每月折算價格；若採季繳，必須清楚顯示季繳總價與有效期間。
保留既有訂閱快照，改價只影響新購／續訂適用版本，不回頭縮減已購額度。
目前程式的版本欄位採每季費用，方案頁的購買按鈕仍停用；改價不等於已完成自動收款、付款驗證與開通。維持目前週期時應建立季繳總價，若要月繳需另實作付款週期與訂閱對帳。

| 對象／方案 | 建議價格 | 起始額度方向 |
| --- | --- | --- |
| 個人雲端免費 | NT$0 | 既有個人核心資料每類 30 筆、題目 50 題、分享 2 人；活動 5／景點 2，不開放雲端圖片上傳 |
| 個人本機 | NT$129／季（折算 NT$43／月） | 本機個人資料依本機版本設定不限制；無雲端分享，公開投稿仍限活動 5／景點 2，不因本機不限量而開放無限雲端圖片 |
| 個人雲端 Plus | NT$99／月或 NT$297／季 | 核心資料每類 300 筆、題目 500 題、分享 5 人；活動 20／景點 5；起始圖片總額度 10 MB |
| 廠商免費 | NT$0 | 活動 5／景點 2；建議圖片總量最多 1 MB，作為試用，不提供無限圖片 |
| 廠商合作 | NT$499／月或 NT$1,497／季 | 活動 50／景點 15、圖片 25 MB；投稿管理與個人成效查詢 |
| 廠商成長 | NT$1,490／月或 NT$4,470／季 | 活動 150／景點 40、圖片 60 MB；較大量投稿、既有可交付的成效功能 |

這些數字是可調整的營運建議，不是寫死的程式 fallback。應儲存在管理員建立的版本與使用者購買快照中。
本機不限量僅指本機儲存，不是無限雲端處理；若本機使用者使用公開投稿等雲端功能，仍須受相應雲端限制。
廠商是否願意付費取決於曝光與轉換價值，須做付費試營運驗證；不承諾流量或成交，不以資料庫空間大小當作唯一賣點。
目前原始 SQL 種子中的廠商價格曾是合作 NT$299／季、成長 NT$699／季；這不等同正式資料庫現在售價。若仍採這種低價，要達到收益目標需要更多付費帳號。

## 四、增加資料量時怎麼加價

不建議「多一位付費者，就替他升級一次 Supabase／Render」。這是共享平台，先出售明確的資源包，再由整體容量決定升級。

| 加購提案 | 建議價格 | 必須同時限制 |
| --- | --- | --- |
| 個人資料包 | NT$49／月 | 個人核心明細每類增加 300 筆；不自動增加圖片、公開活動、景點或後端運算額度 |
| 個人圖片包 | NT$49／月 | 增加 100 MB；預算模型先為每包保留每月 1 GB 圖片傳輸，正式推出前必須完成流量計量及公平使用規則 |
| 廠商投稿包 | NT$199／月 | 增加有效活動 25、景點 5、圖片 25 MB；預算模型每月保留額外 2 GB 傳輸，並非現有程式已具備流量配額功能 |
| 高流量或需獨立處理 | 個別報價 | 外部付費 API、頻繁匯入、專屬運算或獨立環境另行評估；不能承諾以上資源包全部涵蓋 |

現有訂閱倍率會一起放大多種資源。上述「單項加購」不能直接視為現有倍率功能，需另做資源別購買明細與 UI，避免意外把所有限額都放大。
正式提供圖片包前，應先移出 DB 的 base64 圖片、壓縮與產生縮圖、完成 Storage 權限及計量；在完成前不應直接售出大容量方案。

### 加購最低價格的估算式

每包最低月價 ≧（增量運算＋儲存＋流量＋外部 API＋客服維護＋分攤固定成本）÷（1－收款費率－目標貢獻毛利率）。
例如：每包預留成本 NT$10，假設收款費率 3%、目標貢獻毛利率 70%，最低約 10 ÷ 0.27 = NT$37.04，可考慮 NT$49；這是示例，不是已量到每包成本 NT$10。
流量必須包含免費訪客為廠商內容產生的下載，不只算廠商自己進入管理頁。

## 五、升級預算與每月五萬元目標

單一 Supabase Pro US$25＋單一最小 Render paid Web US$7，列價起點 US$32／月，未包含超額、其他服務、較大運算、附加功能與稅費。
若僅用假設匯率 35 做保守預算，不代表即期匯率，約 NT$1,120／月；正式營運初期可先編列 NT$3,000 的平台預算，再依實測調整。

以下是目標情境，不是銷售預測：

| 付費組合 | 人數／廠商數 | 每月認列收入 |
| --- | ---: | ---: |
| 個人雲端 NT$99 | 200 | NT$19,800 |
| 廠商合作 NT$499 | 50 | NT$24,950 |
| 廠商成長 NT$1,490 | 15 | NT$22,350 |
| 合計 | 265 | NT$67,100 |

假設收款成本 3%＝NT$2,013，平台預算 NT$3,000，其他營運 NT$3,000，另預留稅務／退款／波動資金 NT$6,000，示例剩餘 NT$53,087。
此預留不是實際稅率，也未代表聘僱人力或自己的工時已充分計入。若實際費用較高、需支付薪資或商店抽成，售價、數量或成本預算必須重算，不能宣稱此情境必然達到稅後淨利五萬元。
季繳 NT$129 是月認列 NT$43，不是每月 NT$129。所有季繳款應先保留未履行期間的服務成本，不要當月全數當成可支用利潤。

### 商店收費不能用 3% 代替

上面的 3% 只是特定收款合約的假設，並非 App Store／Google Play 的費率。Apple Small Business Program 符合條件並完成加入者可有 15% 佣金；Google Play 的自動續訂與其他交易費率需依地區、方案及付款政策確認。
數位功能或訂閱在商店上架時，必須確認適用付款政策，不能假設改走網站付款就一定免佣金。
以相同 NT$12,000 非收款成本預算試算：若收款／商店費用為 15%，至少需每月營收約 NT$72,942 才有 NT$50,000 餘額；若為 30%，約需 NT$88,572。這仍不是稅後獲利保證。

Google 官方：https://support.google.com/googleplay/android-developer/answer/112622?hl=en

## 六、客戶不續費，是否立即取消平台升級

不能以單一客戶取消就自動降級共用平台。可取消／降級不等於立即退現金或把既有用量歸零。

- Supabase：官方文件說降級立即生效；未用訂閱期間變成 organization credits，通常不是刷退現金，既有超額使用仍會結算。降級前仍須檢查所有專案／使用者容量與仍在使用的付費功能。
- Render：Compute 按實際使用時間計費，改方案須成功部署才套用；降低 Compute 可能增加延遲，降回 Free 也重新受到休眠及共享時數限制。已發生的費用不會因客戶取消而消失。
- 取消一筆客戶訂閱不會移除其他客戶、到期保留一年資料或本月已發生的傳輸。不要為了降級直接刪除客戶資料。

建議先連續觀察 30 天：所有仍有效訂閱都能履約、全部用量與下月預估低於 Free 額度的 50%，沒有依賴付費功能，再由管理員人工確認降級。這是營運門檻提案，尚未建立自動降級。

- https://render.com/docs/compute-plans

## 七、下一階段優先項目

1. 取得兩個平台近 30 天實測數據，分出 database／Storage／egress／Compute／外部 API，建立資源預算。
2. 把 base64 圖片移到受控物件儲存，清單僅載縮圖／連結，避免每次查列表都傳原圖。
3. 圖片上傳大小、公開匯入頻率、成效事件去重及匯出頻率的伺服器端限制；不能只靠前端按鈕。
4. 有效活動筆數與保留一年歷史資料分開計量，後者同樣占空間，不能只收有效筆數卻無限制累積。
5. 不限額度活動仍需平台級安全預算，超量先停止新增或排隊，不擅自刪資料、不自動加購平台方案。
6. 新方案與加購經管理員確認後再發布；尚未設定適用免費版本或有效付費額度時，顯示唯讀並禁止資料異動，管理員可建立初始版本。
