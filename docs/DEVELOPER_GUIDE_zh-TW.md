# Life Pilot 開發者技術文件

本文件依 2026 年 11 月 23 日程式版本 `f6948de9` 重新編寫，說明現行 Flutter App、Supabase 資料層、Edge Function、本機儲存與股票專用後端的責任邊界。資料庫正式狀態仍須以已套用 migration 與函式定義查核，不可只依文件推論。

## 1 系統概觀

Life Pilot 是跨平台 Flutter 應用，主要功能包括帳號與授權、首頁、行事曆、活動與景點、回憶、記帳、積分、遊戲、訂閱、廠商工作台、商業企畫書、回饋及股票。

主要執行邊界如下：

| 邊界 | 責任 |
| --- | --- |
| Flutter App | 畫面、互動、Controller 狀態、本機資料、快取與資料格式化 |
| Supabase Auth | 登入工作階段與使用者識別；註冊及忘記密碼申請由管理員流程處理 |
| PostgreSQL / RPC | 權限、額度、彙總、分頁、交易、分享、帳號生命週期與資料一致性 |
| Supabase Storage | 回饋截圖、帳戶圖片及其他受控檔案 |
| Edge Function `life-pilot-services` | 需要外部服務或秘密金鑰的非股票工作；秘密只存 Edge Secrets |
| Render 股票 API | 僅股票資料更新與查詢的既有路徑；其他模組不得新增 Render 依賴 |
| 本機資料庫 | 此裝置模式的行事曆、記帳、積分、回憶、題目與必要索引 |

## 3 開發環境

主要版本由 `pubspec.yaml` 與鎖檔決定。目前 Dart SDK 約束為 `^3.10.0`，Supabase Flutter 固定為 `2.12.4`。

日常檢查：

```powershell
flutter pub get
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
```

只改特定模組時先跑對應測試，再跑完整測試。測試通過不代表 migration 已部署，也不代表 Android、iOS、Web、macOS 的權限與簽章設定正確。

## 4 MVC 與依賴方向

專案採實務型 MVC 分層：

- View / Page / Widget：只呈現狀態、收集輸入與發出使用者意圖。
- Controller：管理載入、重試、篩選、頁面生命週期、請求世代與通知範圍。
- Model：資料結構、純轉換、排序、驗證與衍生值。
- Service / Repository：I/O、Supabase、Storage、Edge Function、本機資料與交易邊界。

新增功能時應依序建立：資料契約 → Repository → Service → Controller → View → 測試。Widget 不直接拼 SQL 或處理跨表規則；Repository 不操作 BuildContext；Controller 不保管 service role 或外部 API 金鑰。

共用呈現邏輯應放 Widget 或 Formatter，共用資料規則放 Model/Service。避免為測試保留正式環境不使用的舊入口或 RPC 備援；正式函式缺失時，安全相關功能要明確失敗，不可默認成功或零額度。

## 5 啟動與帳號驗證

`lib/main.dart` 先建立可呈現的 App，再延後初始化非必要通知元件，避免權限或外掛阻擋首幀。

帳號啟動狀態分成：

1. 等待驗證：顯示「正在驗證帳號…」。
2. 驗證成功：進入對應首頁或廠商工作台。
3. 驗證失敗：顯示錯誤與重試。
4. 帳號停用：清除可用工作階段並顯示帳號不可使用。

`lib/auth/controller_auth.dart` 使用請求世代與帳號識別避免舊請求覆蓋新登入。Data API 另透過 `pgrst.db_pre_request` 呼叫停用帳號檢查，Storage 也有對應政策，防止舊 Token 繼續寫入。

註冊與忘記密碼由 `ControllerAccountMailRequest` 送管理員申請；管理員建立帳號或臨時密碼。App 不把管理金鑰放在客戶端。

## 6 帳號停用與刪除

帳號生命週期分為有效、停用、刪除申請中與正式刪除。

- 停用：保留資料，阻擋登入、Data API 與受保護 Storage 操作，可由管理員恢復。
- 正式刪除：由管理員確認後移除帳號與涵蓋資料，同一信箱日後可重新申請。
- 待處理刪除申請與停用帳號使用不同清單及分頁契約。

正式刪除 RPC 必須在交易內處理外鍵、分享、訂閱、回饋、內容與 Auth 使用者。新增資料表後要同步更新刪除涵蓋測試，不能只依 `ON DELETE CASCADE` 猜測。

## 7 雲端與本機資料路由

儲存模式由 ControllerAuth 與本機偏好共同決定。Repository 入口應先判斷資料位置，再選擇 Supabase 或 `LocalDataStore`，不可讓 View 自己分支。

本機核心資料包含行事曆、記帳明細、積分明細、回憶及自建題目。雲端投稿、分享及圖片仍受雲端額度限制。

本機模式禁止顯示雲端共享帳戶與共享行程，但不得刪除分享資料；切回雲端後重新取得。任何共享內容查詢都必須同時檢查儲存模式與授權。

## 8 本機索引與固定成本讀取

`lib/local_storage/local_data_store.dart` 維護日期、帳戶、明細 ID、總額、月份統計及預設帳戶等索引。目的不是複製所有資料，而是避免每次啟動掃描完整本機表。

寫入、刪除、搬移或修復資料時必須同步更新索引。舊資料缺索引時，只修補受影響帳戶；避免每次啟動重建全部資料。

索引屬衍生資料，需能由原始資料重建。測試要涵蓋索引遺失、資料變更、帳號切換與同帳戶不同幣別。

## 9 雲端與本機轉移

`lib/local_storage/service_local_data_transfer.dart` 負責轉移協調。

### 雲端到本機

1. 合併查詢轉移初始化、遊戲目錄版本與首頁設定。
2. 匯出個人可搬移資料。
3. 寫入本機暫存並驗證筆數與關聯。
4. 確認後刪除雲端來源及處理分享狀態。
5. 更新儲存偏好與本機索引。

### 本機到雲端

1. 取得雲端方案、累加額度與答題紀錄保留政策。
2. 在送出前檢查整批資料是否超額。
3. 以帶首頁設定的還原 RPC 在單一交易寫入。
4. 比對回傳筆數後才清除本機來源。

遊戲目錄以版本號判斷是否需要重下載；版本相同沿用本機目錄，版本不同或無快取才下載。

## 10 訂閱、額度與唯讀規則

訂閱初始化由 `get_my_subscription_bootstrap` 合併狀態、使用量、累加額度、投稿數與活動期間。Repository 位於 `lib/subscription/repository_subscription_bootstrap.dart`。

重要規則：

- 沒有適用免費、付費或特殊授權版本時，雲端只讀。
- 查詢失敗不能解讀成零額度、免費或已授權。
- 本機有效授權讓核心本機資料不限量；雲端投稿、分享與圖片仍用雲端額度。
- 多筆有效 entitlement 依資源累加。
- `answer_history_days = 0` 表示不保留雲端答題紀錄。
- 特殊授權快照直接保存各項自訂額度、到期日及費用；費用可為零。
- 顯示與計算的數值要使用同一份 resolved quota，不可畫面另行推算。

已完成歷史 entitlement 快照轉換後，不再保留舊欄位名稱相容解析。新增欄位時要同步調整快照、解析、管理表單、檢查約束與測試。

## 11 方案版本鎖定與強制刪除

方案一旦被仍存在帳號或權益引用，禁止修改或一般刪除。資料庫以引用檢查與使用紀錄共同判定。

若使用過該方案的帳號都已正式刪除且沒有剩餘引用，可由受控管理 RPC 重算使用狀態並強制刪除。App 不得直接繞過 trigger 或手動停用所有保護。

計費週期資料未填時依目前規則解讀為月繳。新資料必須明確保存 `month` 或 `quarter`，避免 UI 與資料庫預設不同。

## 12 首頁初始化與早顯示

`lib/pages/home/repository/repository_dashboard.dart` 使用合併 RPC 取得設定、記帳摘要、積分摘要、共享選項、近日行程摘要及推薦內容，降低首屏往返。

Controller 依區塊發布狀態：必要摘要先顯示，推薦、天氣、圖片與其他區塊可獨立完成。失敗區塊可單獨重試，不應把成功區塊清空。

首頁帳戶選擇採游標分頁與資料庫端搜尋，並確保目前已選帳戶包含在首屏。共享帳戶與自有帳戶使用同一摘要模型及呈現元件。

## 13 行事曆、假日與天氣

行事曆以可見月份與相鄰週範圍查詢，並以帳號及月份管理快取。新增、修改、刪除或複製後，只失效受影響月份與首頁摘要。

有結束時間的事件，以結束時間判斷完成提示；沒有結束時間才使用開始時間或日期規則。

假日依語系與年度批次快取；跨年度一次請求所需年度。同年度、同語系的進行中更新共用 Future。

天氣依地點與日期去重後批次呼叫 Edge Function；資料庫快取命中時不呼叫外部服務。預載有並行上限與地點上限，避免卡片大量出現造成尖峰。

## 14 活動、景點與公開匯入

活動與景點查詢在資料庫分頁前排除已到期資料，避免舊資料占滿頁面。清單只選畫面必要欄位；圖片先使用縮圖，預覽才取原圖。

地址解析流程：

1. 合併 RPC 查地圖座標與 geocode cache。
2. 完全未命中才呼叫 Edge Function。
3. 多地址使用批次請求。
4. 取得結果後受控回寫快取與目標資料。

公開活動匯入以批次日期及去重鍵處理，資料庫直接回傳新增、略過與重複統計。外部來源驗證、刪除紀錄與權限檢查不能搬到客戶端。

## 15 回憶走廊與日期游標

回憶首屏使用 `get_my_memory_window` 回傳資料、下一個日期與 `has_more`。`ModelEvent.appendMemoryEvents` 必須使用可變集合或建立新集合，不得把 RPC 回傳的不可變 List 直接追加。

載入更多的目標是：遇到空白日期區間時在同一次操作中繼續前進，直到找到資料或資料庫確認結束。Controller 不應要求使用者重複點擊才能跨過空區間。

圖片解碼分批進行；首批卡片先顯示，剩餘歷史在背景完成。原比例圖片用 `BoxFit.contain` 或等價策略，並限制最大高度以免直式長圖占滿畫面。

## 16 記帳、積分與共享帳戶

自有帳戶總覽、明細與統計使用統一 DTO。總覽帳戶清單採分頁及名稱搜尋；帳戶圖片使用較高解析度縮圖，舊圖缺縮圖時可讀原圖並背景補建。

歷史 RPC 同時回傳指定區間明細、下一頁日期、`has_more` 與總額。保留項不得阻擋繼續尋找一般明細。

共享帳戶以 `ledger_read_shares` 及受控 RPC 管理：

- 收件者依 kind 分頁取得帳戶、摘要、預覽、圖片權限及待審數。
- 預設唯讀。
- 開放提案時，新增、修改、刪除寫入 proposal；核准函式在交易中套用並更新總額。
- 圖片權限獨立；開放後收件者可直接更換帳戶圖片，不經提案。
- 首頁與總覽使用相同摘要，避免核准或原帳戶修改後兩邊數字不同。

任何使用共享表的 RPC 都要以 `security definer` 加上明確驗證，且 authenticated 角色只取得完成查詢所需的 SELECT/EXECUTE 權限。

## 17 統計一致性

統計 SQL 與畫面必須使用相同的方向、日期、幣別、保留項及小數規則。App 不應對資料庫總計再做不同邏輯的二次修正。

修改原始明細、核准共享提案、刪除明細或切換幣別後，應失效：

- 帳戶總覽摘要。
- 明細頁總額。
- 統計序列。
- 首頁摘要。
- 共享收件者摘要。

避免整頁全量刷新；以帳戶 ID、kind 與日期範圍精準失效。

## 18 圖片策略

帳戶、行程、活動、景點與回憶的清單使用縮圖；預覽與編輯按需取原圖。新縮圖以較高畫質 JPEG 編碼，避免重新啟動後只剩低解析舊縮圖。

顯示規則：

- 保留原始寬高比。
- 寬度配合卡片。
- 不拉伸、不強制裁切成 16:9。
- 設定合理最大高度，避免長圖壓縮其他內容。
- 縮圖解碼失敗時可顯示原圖或預設圖，但不可造成整頁失敗。

Storage 上傳只允許已登入角色；models bucket 僅管理員可寫。禁止匿名任意上傳。

## 19 廠商工作台

首次工作台初始化由 `get_my_vendor_dashboard_bootstrap` 內部確保廠商帳號存在，並合併方案、額度、最近投稿與成效摘要。

成效採增量彙總表與短期快取，避免每次掃描全部歷史投稿。新增、編輯、刪除投稿後由 App 局部更新計數與最近五筆，並失效資料庫快取；必要時才重新抓工作台。

`lib/vendor/repository_vendor_dashboard_cache.dart` 管理共用方案資料及快取世代。管理方案成功後只失效方案相關區塊，不應無條件重抓所有成效。

廠商只可查看自己建立內容；`account` 正規化、日期範圍與成效彙總索引必須維持。

## 20 遊戲與題庫

遊戲題目第一頁與群組資訊由合併 RPC 初始化。遊戲進度 RPC 回傳最高通關、近期紀錄、下一頁日期及是否有更多，避免分開查詢。

遊戲目錄有版本號；新增、修改或刪除目錄時同步更新版本。轉移及初始化先比對版本，相同沿用本機快取。

題目字級透過共用響應式元件依可用寬度調整。新遊戲不得自行使用過小固定字級。

離開頁面、帳號切換或控制器 dispose 後，晚到的題目、語音與 WebView 回應必須忽略。

## 21 商業企畫書與回饋

商業企畫書模板讀取與建立使用單一交易 RPC，歷史清單以一次分頁回應傳回資料、游標與是否有更多。狀態寫入序列化，失敗 rollback 不可覆蓋較新的標題或回答。

回饋清單只回傳摘要及截圖 metadata；開啟詳情才取完整內容與檔案。多張截圖預覽有並行上限，避免一次解碼造成記憶體尖峰。舊 Base64 欄位已完成搬移後應保持退役。

## 22 股票資料流

股票模組保留 Render API。初始流程先從 Supabase 取得最新日期與股票內容並立即顯示，再讓外資與期貨各自背景更新。

- 股票、外資、期貨各區塊獨立 loading/error/retry。
- 期貨向前回查上限為 14 天。
- 同日期請求合併，避免初始化、更新前後重複查詢。
- 更新完成或失敗後才開放歷史日期。
- 搜尋同時套用股票與期貨。

不得把股票的 Render 例外擴張到其他模組。

## 23 Edge Function 與外部快取

App 透過 `lib/utils/service/service_cloud_api.dart` 呼叫 `life-pilot-services`。函式處理假日、天氣、地址、公開活動及需秘密的外部整合。

秘密以 Supabase Edge Secrets 管理，不寫入 App、Git、資料表或日誌。一般流程先查 RPC 快取，未命中才呼叫 Edge；同 key 的進行中請求共用。

部署：

```powershell
npx.cmd --yes supabase@latest functions deploy life-pilot-services --project-ref <project-ref> --use-api
```

部署後以 Dashboard Logs 與實際 App 流程驗證，不要把所有 request/response body 寫入 log，以降低 Log Ingestion 與 Log Query 用量。

## 24 Migration 與正式資料庫

所有可部署資料庫變更放在 `supabase/migrations`，依檔名時間順序套用。近期查詢減量涵蓋：

- 首頁設定、摘要、共享選項、近日行程與推薦內容合併。
- 回憶及記帳積分日期游標。
- 假日、天氣與地址批次快取。
- 遊戲題目與進度初始化。
- 廠商工作台合併初始化、快取與增量成效。

部署前先執行唯讀依賴盤點，包含 `pg_depend`、函式定義、動態 SQL 字串、Edge Function 與 App RPC 名稱。確認無舊版 App 或其他程式使用後才能 drop 退役 RPC。

Migration 應包含：交易、函式簽章、權限 revoke/grant、必要索引、schema reload 及可驗證查詢。不可只在 SQL Editor 手動改正式資料庫而不留下 migration。

## 25 權限與安全

- App 只持有公開端可用設定，不持有 service role 或外部秘密。
- RLS 與 RPC 共同保護資料；`security definer` 必須固定 `search_path` 並驗證 `auth.uid()`。
- 管理功能在資料庫再次檢查管理員，不只靠畫面隱藏。
- 停用帳號在登入、Data API、Storage 與敏感 RPC 都要阻擋。
- 分享、特殊授權、方案刪除及帳號刪除採 fail closed。
- 日誌不得輸出密碼、Token、完整信箱清單、service role 或圖片 Base64。

## 26 效能與資料減量策略

| 策略 | 專案實例 |
| --- | --- |
| 合併初始化 | Dashboard、訂閱、廠商、遊戲、分享一次 RPC 回傳首屏需要資料 |
| 資料庫端分頁 | 記帳積分、回憶、企畫書、回饋、成效及管理清單 |
| 游標包含下一頁 | 回應同時帶 `next_date` / `has_more`，不另做探查 |
| 輕量投影 | 清單不取原圖、回饋全文或不需要欄位 |
| 縮圖與延後原圖 | 卡片先顯示縮圖，點預覽才下載原圖 |
| 快取與請求合併 | 假日、天氣、城市、方案與外部地址同 key 共用 |
| 局部更新 | 投稿、提案與明細成功後只更新受影響摘要 |
| 增量彙總 | 廠商成效及本機統計避免重掃全部歷史 |
| 版本比對 | 遊戲目錄同版本不重新下載 |
| 背景載入 | 股票先顯示主資料，外資與期貨各自完成 |

優化不能犧牲正確性：空結果與錯誤要分開；快取必須有明確失效；舊回應不得覆蓋新帳號或新篩選；唯讀與權限判斷不能因 RPC 不存在而放行。

## 27 測試策略

測試分為：

- Model 純邏輯與格式測試。
- Repository RPC 參數、投影、timeout 與錯誤契約。
- Controller 帳號切換、請求世代、重試與局部通知。
- Widget 響應式版面、空狀態、圖片與操作防誤觸。
- SQL migration 靜態契約與函式名稱檢查。
- Android、iOS、Web、macOS 實機驗收。

完整測試目前約三千項；數量會隨版本改變，文件不把某次通過數視為永久保證。CI 失敗時先修正式行為，再更新因介面退役而過時的測試，禁止只刪斷言讓 CI 變綠。

## 28 發佈檢查

1. 確認工作樹沒有意外檔案或秘密。
2. 套用所有必要 migration，執行驗證 SQL。
3. 部署 Edge Function，確認 Secrets 完整。
4. 執行格式、分析與完整測試。
5. 驗證 Android、iOS、Web 與 macOS 的網路、權限、簽章及深層連結設定。
6. 以一般、廠商、管理員、停用帳號、免費、付費、本機與特殊授權帳號驗收。
7. 驗證雲端／本機切換、分享、提案、圖片、分頁與帳號刪除。
8. 觀察 Supabase Database、Egress、Edge Invocation、Log Ingestion 與 Log Query。

## 29 維護原則

- 正確性與資料安全優先於少一次查詢。
- 新查詢穩定並驗證後，刪除退役 App 包裝、測試切換及資料庫 RPC。
- 不保留「函式不存在就當成功」的相容分支。
- 新功能優先擴充正式 DTO 與合併 RPC，不重新引入全表下載。
- 文件、測試、migration 與程式必須在同一次功能變更中更新。
- 所有破壞性操作先以唯讀查詢解析精確目標，再執行受控交易。
